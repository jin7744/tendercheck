## Diagnosis of the two rows first reported as "false met" (B R11 in B-M2 k2 and B-M3 k3)
- Loop: replay both runs at $0 (`--mode replay --replay-from runs/live_20261028_k*/…`), read gold R11 from
  `grade.json`. Red on both, deterministic, about 1 s.
- Finding: not a false met in the product. The model split the bond clause into the bond document (met), a rate
  attribute (met) and a period attribute. The period attribute carried the right status: **error** in B-M2 k2
  (`R15`, period check), **needs-confirmation with C1** in B-M3 k3 (`R15`). The grader's step-5 rule takes the
  shortest record holding any anchor, so it judged the rate fragment.
- Hypothesis 1 (roll attribute failures up into the parent document) was built test-first and **rejected**: the
  fake end-to-end tests went red because 08 deliberately keeps the parent document `met` while its attribute row
  carries the error (A-M3: R12 met, R13 error; 08 §1.3-5, D3). Change reverted, 565 tests green again.
- Open decision (not done): a grader rule for split obligations (judge a gold row by the worst status of the
  fragments that hold its anchors). It would turn 5 rows green without any engine change, which is exactly why it
  needs a stated reason and a flip list before anyone adopts it.

No mismatch in these 18 runs shows `met` where the product output lacks the right status somewhere. The closest is
`conditional/not_triggered` read as `met` (A R16 k3, B R14 k3): a rule that does not apply to a single bidder shown
as satisfied.

### T03 HOLD (k2, k3): aux check "time-zone conversion" failed
The model's `deadline.raw` for Body §5 was "30 November 2026, 14:00 hours" in k2 and k3; the quoted sentence ends
"Corvessa time (UTC+03:00)" and k1's raw kept it. With no zone in raw and no `tz_quote`, code had nothing to convert
with, so the row said nothing about 20:30 KST = 14:30 UTC+03:00. The Annex 1 deadline kept its zone through
`tz_quote` ("All times in this Bid Data Sheet are Corvessa local time (UTC+03:00).") in all three runs.

**Fix 5 (d5b1d29):** Q5 re-reads raw with the record's own verified quote as the zone source when raw and
`tz_quote` give none, only if the quote yields one zone without error (two different zones, or a bad offset, leave
it unstated as before). `tz_source` = `quote`. Tests with literal expectations in `test_deadline_zone_from_quote.py`.
Replayed k2 row now reads: "Planned upload 2026-11-30 20:30 UTC+09:00 = 2026-11-30 14:30 UTC+03:00: after the
Body §5 deadline (2026-11-30 14:00 UTC+03:00); before the Annex 1 ITB 23.1 deadline (2026-12-02 14:00 UTC+03:00)."

### T02 FAIL (k2): critical check "R07 met + triggered" in B-M1 got met with no condition
Gold R07 (사용인감계) has two anchors on two lines: 공고문 3.⑥ "사용인감을 날인하는 경우에 한하여" and 별첨 서식 제3호
"사용인감과 법인인감을 함께 날인". The engine gave two records: R09, the form, conditional on `usage_seal` (triggered,
met), and R27, the seal rule of the form, `attribute_of` R09. The grader takes the shortest quote holding an anchor
(08 §4.1-5, written before the build), so it graded R27. In k1 the model had repeated the condition on the seal
record, so it read met + triggered; in k2 it did not, and code only passed a parent's unknown or not_triggered state
down to its attributes, not triggered.

The grader was not changed: the rule is from the test specification written before any result existed. The
engine was inconsistent (the same row read "met (applies)" or plain "met" depending on the model), so the fix went
there.

**Fix 6 (edbdc04):** an `attribute_of` row without its own condition inherits a triggered parent and is judged by
the lower rules (it already inherited unknown and not_triggered). Reasons for such rows name the parent's condition
("사용인감을 날인하는 경우에만 필요하며 …") instead of "원문에 적힌 조건에 해당하는 경우".

### T02 HOLD (k1): threshold "remaining B-M3 rows" 17/18
Gold R17 (제안요청서 Ⅳ-4, merge rule, expected met) read conditional / unknown. The model marked the record
`mandatory` and attached "공동수급인 경우 ⑫ 포함" as a consortium condition. Those words say which documents join
the merge, not whether the rule applies (the prompt says a record with conditions is `conditional`, so this is a
prompt slip). Across all 10/28 runs the model did this 8 times: 5 on this merge rule, 3 on seal rules of JV or
usage-seal forms (those really are conditional). It is worse than the HOLD shows: for a single firm the same record
reads "공동수급으로 참가하는 경우에만 필요하며, 목록에 해당하지 않는다고 적혀 있습니다", i.e. a rule that binds
everyone reported as not needed. That is fail-open.

**Fix 7 (c616453):** after the last model stage, a file rule (format, naming, merge) that the model itself marks
`mandatory` loses such a condition (`verification_log.file_rule_scope_conditions`). Rules marked conditional and all
non-file records keep their conditions, so a conditional document still never reads missing (08 T02). Narrower
than "ignore conditions on mandatory records", which would have broken the three seal rules.
